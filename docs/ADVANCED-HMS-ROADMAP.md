# Medora Advanced HMS Roadmap

## Objective

Evolve Medora from its current administration, patient-registration, doctor, and appointment foundation into a production-oriented hospital management system for Indian hospitals and clinics.

The implementation will be delivered as tested vertical slices. Existing authentication, role-based access control, patient registration, doctors, appointments, migrations, and seed workflows must remain working after every increment.

## Product scope

### Phase 0: Foundation hardening

- Environment validation and safe development setup
- Consistent API error contracts and request validation
- Pagination, filtering, audit logging, and soft-delete conventions
- Automated backend tests and frontend build checks
- Secure secret handling and removal of default production credentials

### Phase 1: Front office and OPD

- Patient registration, search, duplicate detection, MRD numbering
- Appointment booking, doctor schedules, check-in, cancellation, rescheduling
- OPD visits, queue/status tracking, consultation handoff
- OP check-in now separates waiting patients from those called into consultation. Staff with `visits.consult` can start an open OP consultation once; the visit records the actor and time and writes a patient audit event. The Check-in list filters waiting and consulting patients, orders each doctor's waiting queue by token, and still allows checkout. Doctor token allocation and the shared visit/OP number sequences are serialized across concurrent check-ins. This is a staff-operated status transition, not an automated appointment handoff or a clinical encounter signature.
- Consulting patients have an Open chart action in the queue for staff with `clinical.view`. A new draft encounter opened through that route carries the OP visit ID; the server verifies patient ownership, derives the assigned doctor from the visit, and rejects a conflicting doctor ID. Historical and closed visits can still be linked through the encounter API; visit state is not a clinical signing gate.
- Appointment Check-In now uses the same OP visit transaction as the check-in form. Both paths allocate the doctor's token, create a waiting queue visit, link the appointment, and record appointment status history atomically. A patient with an open OP visit cannot be checked in again through the appointment action.
- Checking out an OP visit completes its linked checked-in appointment(s), writes appointment status history, and records a patient audit event in the same transaction. The Appointments page directs staff to the OP queue while a linked visit is open. A direct appointment completion request is rejected until checkout and is serialized with concurrent checkout.
- Registration sources and patient communication history

The existing registration source catalog is available to the registration form. Staff can select an active source when creating or editing a patient; the API validates it, stores its ID, and returns its name on the chart. Existing patients can retain an empty source. The seed provides Walk-in, Referral, Online, and Medical Camp. Administrators with `patients.registration_sources.manage` can add sources, rename them, retire them, and reactivate them. Codes cannot be edited; retiring a source prevents new assignments while preserving the name on historical charts. Seeding only inserts missing defaults and preserves admin edits. New catalog changes are recorded in an append-only event table with actor, time, and before/after name and active state, and the admin page shows the latest 100 events for a source. Sources created by earlier seeds have no creation event. A date-range report (up to 366 inclusive days) counts patient records by `registration_at` and their current source assignment, including inactive, merged, and unassigned records. Its dates follow the MySQL session local time; later source edits can change historical totals. It is a current-attribution report rather than an immutable acquisition cohort. Run migrations and the seed after deployment to add the event table and permission, then grant the permission to designated administrators.

Patient merge now moves visit, clinical, pharmacy, billing, and operational records to the surviving chart in one transaction while retaining the source identity and audit trail. It rejects merges when both records have active admissions or both have active emergency cases; staff must resolve those workflows first. The merge audit stores the source and target IDs and counts of moved records. Unique contact and identification details remain attached to the inactive source record for manual review.
Patient search by MRD or free text also resolves a merged source MRD to its active surviving chart. The registration page has a dedicated MRD lookup for this purpose; the main table search remains a local filter of loaded rows.
Staff with `patients.merge` can start a merge from the source row, search and select the surviving chart, review the consequence, and type the source MRD to confirm. The server remains responsible for validating both records and rejecting conflicting active care.

Current communication history: authorized staff can manually record inbound or outbound patient contact by phone, SMS, email, in person, or other channel, including subject, summary, time, and optional follow-up due time. Entries are append-only, patient scoped, audited, and shown on the patient dashboard and timeline. Staff can complete a follow-up with a note; open and overdue tasks appear in the patient API, and an open queue appears on Operations for users with patient view permission. Recording an SMS or email here does not send it.

### Phase 2: Clinical EMR

- Patient timeline and encounter history
- Vitals, allergies, medical history, diagnoses, clinical notes
- Prescriptions, medication history, attachments, consent records
- ICD-10/ICD-11-ready diagnosis catalog and clinical audit trail

Current allergy workflow: staff can record, review, and remove patient allergies in the clinical panel; changes are recorded in the patient audit log. Recorded allergies are also surfaced near the top of the patient dashboard for clinical viewers. Prescription creation, patient-linked stock dispensing, and recording a medication as given block exact case/whitespace-normalized matches against the entered medicine name and catalog medication brand/generic names. Nurses can still record a dose as withheld or refused with a reason. This is a basic safety check only: it does not detect drug classes, ingredients, synonyms, cross-reactivity, interactions, or dosing risks. Clinical review remains required.

Current medical history workflow: staff can add dated conditions with notes, review them in the patient clinical panel, and remove mistaken entries. Additions and removals are recorded in the patient audit log.

Current diagnosis catalog: users with `clinical.catalog.manage` can add local, ICD-10, or ICD-11 labeled terms with a code and optional source version, and deactivate terms for future use. Clinicians can search active terms and select one when creating an encounter; the server resolves and snapshots the term ID, code, system, name, and version, rejecting inactive terms. The chart displays the saved code and version. Two catalog releases may use the same code, while each encounter keeps the version chosen at the time. Free-text diagnoses remain available for uncoded notes. The catalog is initially empty: Medora does not import, validate, license, or claim completeness of any official coding system. Hospitals must verify each imported or entered term against their approved terminology source before clinical use.

Current encounter finalization: users with `clinical.update` can sign a draft encounter that contains clinical content. Signing records the user and time, rejects repeated signing, adds a patient audit entry, and appears in the timeline. Signed content is not edited in place. Authorized staff can append dated addenda with a reason and author; the original note remains intact, and each addendum is visible in the chart, audit trail, and timeline. This is an internal attestation, not a cryptographic or legally verified electronic signature.

Authorized clinicians can edit an unsigned encounter draft's narrative, vitals, and diagnosis. Every save requires the revision read by the editor; a stale revision or a signed encounter rejects the edit. A successful save increments the revision and records the actor, changed field names, and diagnosis identifiers in the patient audit trail without copying clinical free text or vital values. The current draft contains the latest text; prior draft text is not version archived. Signed content continues to require an addendum.

Creating a draft encounter also writes a patient audit entry in the same database transaction. The audit API exposes the action and actor summary; the stored record retains the encounter ID and diagnosis fields for internal traceability.

Current consent workflow: authorized staff can attach a PDF or image copy of a signed consent, record its purpose, risks explained, language, signatory and signature time, and, for specific consents, the treating doctor and registration number. The chart lists records without returning file contents; document retrieval requires clinical view permission. Revocation preserves the original copy and records a reason and audit entry. Staff must verify the uploaded copy and identity: Medora does not validate the signature, establish the signatory's legal authority, or certify consent compliance. The fields were informed by the [Clinical Establishments hospital consent guidance](https://www.clinicalestablishments.mohfw.gov.in/sites/default/files/2022-06/885.pdf); the hospital must review the workflow against its procedures before clinical use.

Current patient timeline: the Timeline tab combines up to 100 recent events from registration, appointment status history, visits, encounters, prescriptions, admissions/discharges, laboratory and radiology orders/results, emergency and surgery cases, consent, and allergy/medical-history audit changes. It is patient-scoped and requires clinical view permission. This is a recent-event summary rather than a complete legal record or an unbounded event archive.

Current patient chart tabs: Profile and MRD show identity details and audit history; Visit, Bills, Tests, Rx, and Appointment load patient-scoped records from the existing modules. Tab data is read-only and follows the corresponding API permission checks. Further workflow actions remain in their dedicated modules.

### Phase 3: IPD and nursing

- Admissions, wards, rooms, beds, transfers, discharge
- Nursing station, care plans, observations, medication administration. The inpatient overview now lists active admission care plans whose scheduled review time has passed, with pagination and a direct review action. Completed or discontinued plans and discharged admissions leave the queue. Plans without a scheduled review time do not appear; escalation still needs design.
- Staff can continue an active care plan after documenting a review and scheduling the next future review. Each continuation is append-only, retains the previous due time, names the reviewer, updates the due queue, and writes a patient audit entry. The panel shows continuation history for active and closed plans; completion and discontinuation remain separate outcomes.
- Inpatient admissions now have an append-only nursing handoff record with condition, pending tasks, optional safety concerns, outgoing staff, an assigned receiving account, and receiving staff acknowledgement. The receiver must be an active account with both inpatient view and update permissions; only that account can acknowledge, and outgoing staff cannot assign themselves. Another pending handoff cannot be created for that admission until acknowledgement or discharge closure. Discharge closes any unacknowledged handoff in the same transaction, retains the note and assignment, records the actor, and adds a patient audit entry; existing discharged handoffs are backfilled with a closure time. Creation and acknowledgement are patient audited without copying clinical note text. Staff can review handoff history from the admissions table. The inpatient overview has a paginated queue of pending handoffs for active admissions, showing placement, assigned staff, and a staff-selected acknowledgement deadline without the clinical note. Overdue items are highlighted and ordered by due time. Assignment and reassignment create staff-specific in-app notices in the same transaction, containing the admission reference but no clinical note or reassignment reason. Earlier handoffs have no deadline; this is visibility, not an automatic escalation or a mandated clinical interval. Staff granted `inpatient.view`, `inpatient.update`, and `inpatient.handoff.reassign` can redirect an unacknowledged handoff to another eligible account with a reason; every reassignment remains in a separate immutable history and patient audit. Run the seed after deployment to add the permission, then assign it to designated supervisors. Assignment is to a staff account, not yet derived from the duty roster; automatic supervisor escalation remains outstanding. Older handoffs created before assignment support remain unassigned and may be acknowledged by eligible staff.
- The pending handoff queue can now filter on handoffs assigned to the signed-in staff member and on overdue deadlines. Filtering and pagination run in the database, so older matching handoffs are not hidden by the first page. An overdue filter excludes handoffs without a deadline. This remains a visibility tool; it does not automatically notify supervisors or reassign an overdue handoff.
- Staff granted `inpatient.view`, `inpatient.update`, and `inpatient.handoff.escalate` can manually alert another eligible staff account about an overdue, unacknowledged handoff. The escalation has an append-only reason and actor history, a patient audit entry, and an in-app notification containing only the admission reference. Duplicate alerts to the same recipient are rejected. Escalation does not change the assigned receiver or replace direct clinical follow-up. The seed adds the permission; administrators must grant it to the intended staff roles. Roster-based supervisor routing remains outstanding.
- Due care plans and pending handoffs now open their admission through a permission-checked lookup by admission ID. A dashboard queue item can be opened even when its admission was added after the dashboard's initial list loaded.
- In-app handoff assignment, reassignment, and escalation notices now have a View handoff link. It resolves the handoff to its admission through an inpatient view protected API and opens the handoff panel directly, including when the handoff has left the pending queue. The link contains only the handoff identifier; the API supplies patient details after authorization.
- The API now checks pending handoffs for overdue deadlines on startup and once per minute. It sends one in-app reminder to the current active, inpatient-authorized receiver for each assignment, records the send time and patient audit event transactionally, and resets reminder eligibility when a handoff is reassigned. The reminder contains only the admission reference and links to the handoff. It does not page staff, contact an external channel, or automatically escalate to a supervisor. Large backlogs are processed in batches, up to 1,000 candidate handoffs per run.
- The pending handoff queue shows when its current assigned receiver was reminded. Reassignment clears that timestamp until a reminder is sent to the new receiver.
- Discharge summaries and follow-up instructions
- Completed admissions expose a read-only discharge view with diagnosis, clinical summary, medication review, follow-up instructions, admission/discharge dates, and a print layout. Discharge now requires a clinician with inpatient and clinical update permissions to review every active recorded prescription, choose continue with instructions or stop with a reason, and attest even when none are active. The server rechecks the list, stops selected prescriptions, saves an immutable decision snapshot, and audits the discharge in the same transaction as bed release. This is a review of Medora's active prescriptions, not a complete reconciliation of outside/home medicines, a new take-home prescription, or a certified signature. See [discharge review design](INPATIENT-DISCHARGE-REVIEW.md).
- Continuing a recorded prescription at discharge now rechecks the recorded allergy list against the prescription name and any linked catalog brand/generic name; a match rejects the discharge and rolls back the review. This is limited to exact normalized names and still requires clinical judgment.
- The patient chart now records source-labeled home medicine history separately from Medora prescriptions. Discharge requires review decisions and attestations for both lists; stopped home medicines are marked not current and both sources appear separately in the discharge print view. The reported list is not automatically verified or imported from external sources; see the [discharge review design](INPATIENT-DISCHARGE-REVIEW.md).
- An active admission now has an explicit review of current reported home medicines, including continue, hold, or stop decisions, an empty-list attestation, a source-preserving snapshot, and patient audit. New medicines reported later can receive append-only follow-up decisions. This records the admission decisions without creating inpatient prescriptions; see the [admission review design](INPATIENT-ADMISSION-MEDICATION-REVIEW.md). Continuing a medicine at discharge after it was held or stopped at admission requires a documented explanation.
- The patient timeline now includes reported home medicine intake and cessation, initial admission medication review, and follow-up review events. It shows an overview; source details and individual decisions remain in their clinical and inpatient views.
- Bed occupancy and ward dashboards
- Admission, bed transfer, nursing observation, medication administration, and care plan creation/closure now write attributed patient audit entries in the same transaction as the care record. Audit metadata uses record identifiers and decision/status fields; clinical free text stays in the underlying permission-controlled records. Earlier records are not backfilled.

### Phase 4: Billing and revenue cycle

- Charge masters, packages, invoices, receipts, refunds
- Insurance, corporate accounts, approvals, claims-ready records
- Patient ledger, discounts, taxes, payment reconciliation
- Financial reports and cashier controls
- Billing now has a date-range cashier report (up to 90 days) with payment-method receipt counts, refund counts, gross receipts, refunds, and net collections. Dates follow the MySQL session local time and totals come from stored transaction amounts; the report does not represent historical outstanding balances. Bank reconciliation remains future work.
- The cashier report can now be downloaded as a UTF-8 CSV with the selected date range, payment-method totals, staff cash totals, and overall totals. The export uses the same validated range and `billing.view` permission as the on-screen report, sets no-store, and escapes spreadsheet formula prefixes in staff names. It is an aggregate report, not a bank reconciliation or transaction-level deposit file.
- Billing now has a current receivables report for open and partially paid invoices with a positive balance. It groups unpaid amounts by due date (no due date, not yet due, 1–30, 31–60, 61–90, and over 90 days overdue) and provides a paginated, permission-checked invoice list. The age is measured against the database session's current date; a refund changes the current balance. This is not a historical as-of ledger or a payer claim aging report.
- Staff with billing view access can open and print a payment receipt from an invoice. It shows the patient MRD, invoice, payment method and reference, and any refunds against that payment, with current net retained. Payment ID is the lookup identifier; it is not a tax invoice number or a regulated receipt sequence. Printed copies reflect the refund state at viewing time rather than an immutable archive.
- The cashier report now breaks cash receipts and cash refunds down by the staff account that recorded each transaction. Older transactions without an actor appear as Unassigned. A refund is attributed to the staff member who recorded the refund, which can differ from the original payment recorder.
- An authorized cashier can close their cash for the current database-local date once, recording expected cash receipts less cash refunds, counted cash, signed variance, reason when the variance is nonzero, staff identity, and close time. Supervisors with billing view access can review closeouts by date. Further cash payments and cash refunds by that cashier on the closed date are rejected; noncash transactions remain available. This is a daily cash count and lock for the recording account, not a physical drawer or bank deposit reconciliation.
- Staff granted `billing.deposit` can record partial or full bank deposit references against a closed cashier day. The register retains amount, deposit date, bank reference, note, actor, and record time separately from the immutable closeout. A row lock and cent-based calculation prevent concurrent postings from exceeding counted cash; duplicate references for one closeout are rejected. Staff granted `billing.deposit.void` can correct an erroneous entry through a reasoned, attributed void; the original row remains visible and its amount becomes available again. `billing.view` users can review the register by closeout date. Run the seed after migration and assign both deposit permissions only to staff authorized to control deposits. This is an internal deposit register; Medora does not confirm bank receipt or match bank statements.

### Phase 5: Pharmacy and inventory

- Drug catalog, batches, expiry, stock ledger, locations
- Purchase orders, suppliers, goods receipt, stock transfers
- Pharmacy dispensing and prescription fulfillment
- Pharmacy inventory dispensing and dispense-history forms now search active, unmerged patients by MRD or name, replacing free-entry patient IDs. General stock issue may still omit a patient; prescription fulfillment requires one. The limited lookup returns ID, MRD, and name under `pharmacy.inventory.view`, and the dispense service rejects merged patients. The browser smoke check opens both pharmacy forms without creating a stock transaction.
- Pharmacy inventory now shows Receive stock only to users with `pharmacy.inventory.create` and Dispense stock only to users with `pharmacy.inventory.update`. Inventory viewers can still search dispense history. The API permission checks remain the authority for these actions.
- Prescription fulfillment locks the prescription and inventory batch while checking previously dispensed quantity and available stock. The isolated integration suite now sends simultaneous issues against a one-unit prescription and verifies exactly one succeeds.
- Patient-linked pharmacy dispensing now writes an attributed patient audit event in the same transaction as the stock movement. Its metadata records transaction, batch, medication, prescription, and quantity identifiers without copying free-text issue notes or references. The patient timeline shows the dispense event; general stock issues without a patient remain in the inventory ledger only.
- Prescription creation now checks that the patient remains active and unmerged, validates the encounter, medication, and recorded allergy list, then saves the prescription and an attributed patient audit entry in one transaction. Audit metadata identifies the prescription, linked records, and quantity without copying medication instructions. The existing patient timeline continues to derive its prescription event from the prescription record.
- Pharmacy batch reconciliation now uses a separate `pharmacy.inventory.adjust` permission. Staff enter a physical count and reason; the server locks the batch, rejects an unchanged count or a stale expected quantity, and records the signed difference and staff member in the stock ledger. Inventory viewers can page through receipt, dispense, and adjustment movements for a batch. The movement view shows adjustment reasons and receipt references but excludes dispense notes and patient details. Run the seed after deployment so the new permission appears in role management; assign it only to staff authorized to correct stock counts.
- Stock receipt now uses the active medication catalog in the form instead of asking staff to type a numeric medication ID. The receipt API still verifies that the chosen medication remains active when stock is posted.
- The dispense picker hides expired and empty batches, shows expired stock distinctly, and identifies the earliest usable batch that can supply the requested quantity. The API checks expiry against the database session's current date. When staff select a later eligible batch, the API requires a reason of 5–500 characters and records it on the stock movement for inventory reviewers. This is a single-batch FEFO check; it does not split an issue across batches.
- Reorder levels and stock/expiry alerts

The operations dashboard now separates three inventory risks using the database's current date: usable batches at or below their reorder level, positive stock already expired, and positive usable stock expiring within 90 days. Empty batches no longer count as expiry risk, and expired batches no longer inflate the reorder alert. The pharmacy inventory summary shows expired and expiring batches separately. These are review counts, not automatic supplier orders or a quarantine action.

Operations stock alerts link to the corresponding filtered pharmacy inventory view for users with inventory view access. The pharmacy page also provides All, Low stock, Expired stock, Expiry watch, and Quarantined filters and keeps the selected filter in the URL so staff can share or revisit the worklist. The inventory table now uses the paged worklist described below.

The inventory table now uses a permission-checked database worklist with bounded pages, server search, alert filters, and exact summary totals across all active batches. Dispensing uses the focused medication lookup described below.

The dispense form now searches stocked medications by brand, generic name, or code through a bounded lookup, then loads eligible batches for the chosen medication or active catalog prescription. Empty, expired, and quarantined batches are excluded by the database. FEFO suggestions use the complete eligible batch set for that medication; the dispense transaction still rechecks stock, expiry, hold, prescription, allergy, and FEFO conditions. The legacy unpaged inventory endpoint remains for compatibility with existing callers.

Inventory adjusters can quarantine an active batch with a reason, immediately blocking patient and general stock dispensing without erasing its quantity. A receipt into that batch preserves the hold. Releasing a batch requires another reason and is forbidden after expiry. Quarantine and release are staff-attributed, zero quantity stock ledger events, and the movement panel shows both reasons. The inventory and operations views show held batches separately. This supports a manual quality hold; Medora does not verify inspection evidence or implement recalls across suppliers or sites.

Held batches are excluded from FEFO eligibility and from usable low-stock and near-expiry alerts. Expired stock with remaining quantity still appears in the expired-stock alert even when held. The API's `lowStock=true` inventory query uses the same usable-batch rule as the operations dashboard.

Inventory adjusters can record disposal of a positive quantity from a quarantined or expired batch. The server locks the batch, requires the quantity seen by the operator to still match, prevents overdrawing and disposal of usable unheld stock, and records a signed stock movement with reason and staff. Partial disposal leaves the remainder visible for follow-up. This records an inventory reduction; the hospital must carry out physical destruction and any required external documentation separately.

### Phase 6: Laboratory and radiology

- Test catalog, panels, sample collection, lab workflow
- Results entry, validation, release, printable reports
- Radiology orders, scheduling, reports, document attachments
- Integration-ready interfaces for LIS/RIS/PACS

Current laboratory reporting: samples are collected with a recorded specimen label before a draft result can be entered. A separate user with `laboratory.verify` must attest to patient/specimen and QC review; the draft author cannot verify their own entry. The verifier explicitly classifies whether a result meets the local critical-result criteria and documents a reason when it does. A linked active referring doctor receives an in-app notice at critical verification without result details; direct contact remains required. A user with `laboratory.release` then publishes the verified result, at which point a linked referring doctor receives a completion notice without result values. View-only users see released values only. Verified and released results cannot be overwritten through draft entry. Authorized staff can append dated corrections with reason and author after release; the original result remains intact and a linked doctor receives an in-app notice. Orders persist requested priority and clinical notes; older orders receive routine priority when migrated. Historical completed orders have no verification metadata. This internal workflow is informed by the [WHO laboratory result review guidance](https://extranet.who.int/lqsi/content/start-reviewing-and-authorizing-results-ie-validation-results-releasing-report); it does not check actual QC evidence, provide a regulated signature, infer critical values from thresholds, enforce escalation deadlines, or integrate with an LIS. Formal correction approval remains outstanding.

Released laboratory results now have a browser print view with patient, order, specimen, original result, addenda, and review/release details; verified drafts have no print action. A formal signed report and immutable PDF archive remain outstanding.

The laboratory order form now searches active, unmerged patients by name or MRD through a bounded, minimal lookup authorized by `laboratory.create`, and requires a patient selection before submission. It can also select an active referring doctor by name, code, or registration number, enabling result and correction notices when that doctor has a linked login.

Laboratory catalog managers can add tests with code, name, category, default priority, turnaround time, and price, retire tests from future ordering, and reactivate them later. Existing orders keep their test reference and name. Revisions remain outstanding.

Staff with `laboratory.cancel` can cancel an uncollected order with a recorded reason, actor, and time. Collected or later orders reject cancellation, and cancelled orders cannot progress through specimen collection or results.

Released laboratory results now have append-only contact attempts and confirmed-delivery records with recipient, method, time, summary, and staff attribution. The patient audit trail records each contact without copying result details into its summary. This supports urgent-result escalation documentation; staff must still follow hospital contact and escalation procedures.

The laboratory workbench now pages and searches on the server, with status filtering and exact overall KPI counts. The API limits each worklist page to 100 orders; the legacy unscoped list is capped at 100 for compatibility. Patient-scoped history still uses the existing list endpoint.

The laboratory workbench now has a paginated [result communication queue](LABORATORY-COMMUNICATION-QUEUE.md) for verified urgent, STAT, and explicitly classified critical results without confirmed delivery, including those awaiting formal release. Released result corrections of any priority return to the queue until the latest addendum is communicated. Authorized staff can record direct contact after verification. Attempts remain visible until a delivered contact is recorded. It does not infer critical values from test results or enforce an escalation deadline.

Current radiology reporting and scheduling: the study name entered in the UI is persisted. Pending studies can be booked for a future time and rescheduled with a reason; an append-only history records prior times and actors. Resource managers can register scanners or rooms by modality; assigned bookings include a duration and are protected against overlapping scheduled studies by a resource row lock. Unassigned bookings have no collision check, and staff/maintenance/external schedules are not integrated. Staff mark a study performed before finalizing a nonempty report. Drafts can be edited while performed; a final report cannot be overwritten through the reporting endpoint. The status update uses a row lock, so concurrent finalization attempts produce one final record and one doctor notification. A linked active doctor account receives an in-app notification without patient details or report text. The UI shows final reports read only and supports dated, append-only addenda with a reason and author. Linked active referring doctors receive an in-app addendum notification without findings. Staff can append attempted and delivered nonroutine finding communication entries after performance, recording recipient, method, finding summary, time, and recorder; the application does not detect critical results, verify actual receipt, or escalate overdue contact. Clinician attestation, image management, and external RIS/PACS integration remain outstanding. The final-report boundary is informed by the [ACR communication practice parameter](https://www.acr.org/-/media/acr/files/practice-parameters/communicationdiag.pdf); this implementation is not a claim of compliance.

The radiology workbench now has a paginated [finding communication queue](RADIOLOGY-COMMUNICATION-QUEUE.md) for performed urgent/STAT studies and corrected final reports awaiting confirmed delivery. Finalizing an urgent/STAT report or appending a correction starts a new follow-up period even when an earlier finding was delivered. Contact attempts before that milestone are not counted toward the new obligation. This still requires staff to use the hospital's escalation process.

The radiology order worklist now pages and searches on the server, filters by status, and computes KPI counts across all orders. Pages are limited to 100 rows. The legacy unscoped order list is capped at 100 for compatibility, while the patient-scoped history endpoint remains available to the patient chart.

View-only radiology staff now see draft study status without draft report text or impression in order lists and the worklist. Free-text finding summaries and notes in communication history are also withheld from view-only staff until the report is final. Staff with `radiology.update` can review draft content to complete reporting and direct contact. Finalized content remains available to `radiology.view`.

Staff with `radiology.cancel` can cancel an ordered or scheduled study with a reason. The transaction stores actor and time, adds a patient audit entry, and notifies a linked active referring doctor without putting the reason in notification text. A cancelled scheduled study no longer blocks its scanner slot; its prior booking and schedule events remain for review. Performed and reported studies cannot be cancelled.

Radiology creation, scheduling and rescheduling, performance and draft saves, finalization, addenda, and finding contact now write attributed patient audit entries in the same transaction as the source change. Audit metadata identifies the affected record and workflow state without copying report text or communicated findings. The patient timeline surfaces scheduling, performance, correction, contact, and cancellation milestones alongside the existing order and final-report events.

Finalized radiology reports now have a browser print view containing patient and study identifiers, report and impression, dates, reporting staff, and dated addenda. Printing waits for addenda to load successfully and excludes the correction form. This is a browser printout, not a signed or archived PDF.

Finalizing a new radiology report requires an explicit reporting-staff review confirmation for the patient identifier, study, report, and impression. The API rejects finalization without it and records the confirmation in the patient audit event. This is an internal attestation; independent image review, regulated signatures, and external PACS remain outstanding.

Radiology order entry now searches active, unmerged patients by MRD or name and requires the staff member to select a result. The lookup returns only ID, MRD, and name under `radiology.create`; entering an unchecked numeric patient ID in the form is no longer possible.
The local browser smoke check exercises the patient search and selection when an active patient exists, without submitting a new order.

### Phase 7: Operations and integrations

- Operations dashboard KPI totals now use full database counts and billing balance aggregation; preview queues remain bounded. Waiting appointments count checked-in patients. The CSV export includes KPI and alert totals and escapes spreadsheet formula prefixes in patient-entered text. The isolated integration suite covers values beyond the preview limits.
- A read-only FHIR R4 Patient export is available at `GET /api/fhir/r4/Patient/:id` and from the patient dashboard for users with `patients.export`. It maps MRD identifier, name, contact, address, administrative gender where directly representable, recorded birth date, active status, and merged-record replacement link. Medora's `transgender` value is exported as text in the R4 patient gender identity extension; it is not assigned an administrative gender code because that field does not establish one. Each access is audited in the patient log, and responses use `application/fhir+json` with `no-store`. The mapping follows the [HL7 FHIR R4 Patient resource](https://hl7.org/fhir/R4/patient.html), [R4 gender identity extension](https://hl7.org/fhir/R4/extension-patient-genderidentity.html), and [FHIR HTTP content type](https://hl7.org/fhir/R4/http.html). This is a single-resource export, not a complete FHIR server, profile validation, ABDM integration, or external data exchange. Set a stable HTTPS `APP_URL` before relying on the MRD identifier namespace outside development.
- OT/surgery, emergency/triage, ambulance, blood bank. Blood bank now has unit receipt into quarantine, screened release, patient issue with a recorded crossmatch reference, discard, and append-only status events behind separate view/manage/issue permissions. ## Architecture rules

- Database migrations are the only production schema change mechanism.
- Each feature is implemented as a vertical slice: migration/entities, validation, repository/service/controller, route, frontend API/types/UI, tests, and seed data where needed.
- Permissions are database-backed and checked at the API boundary; the frontend only hides unavailable actions as a usability feature.
- Patient and clinical data changes must be auditable.
- Destructive operations use soft deletion or explicit confirmation whenever possible.
- No external product source code, branding, or proprietary assets will be copied.

## Verification gates

Every increment must pass:

- Backend type checking/build
- Frontend production build
- Relevant automated tests
- Migration/seed verification against a clean database where schema changes are involved
- Manual browser verification for user-facing flows
